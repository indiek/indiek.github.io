Contributing

IndieK opens to external contributions on 1 November 2026. Until then, this page describes how the project works, so you can get familiar with the code and the format; the channels for issues and contributions will be announced here on that date.

Development workflow

The project uses uv for everything Python.

uv sync                                       # create the environment
uv run pytest                                 # the test suite
uv run pytest -m slow                         # the 10,000-event performance test
uv run ruff check src tests scripts           # lint
uv run ruff format --check src tests scripts  # formatting
uv run ik --help                              # the CLI from your working copy

Rules for every change

  • Tests first. Every feature and every bug fix comes with tests; the suite must stay green, lint and formatting clean.
  • A changelog entry in CHANGELOG.md, in the section of the upcoming release.
  • Versioning. The package follows semantic versioning: a new feature bumps the minor version, a fix the patch version.
  • Small, focused changes, with modern, fully typed Python.
  • The README examples are executed by the tests: keep them runnable.
  • The SDK never imports CLI dependencies (rich, python-dotenv); a test enforces it.

Changing the format

The format is the part of IndieK that must last, so changes to it follow stricter rules:

  1. Update SPEC.md, the normative specification, in the same change as the code.
  2. Regenerate the test vectors with uv run python scripts/make_test_vectors.py and explain any changed value.
  3. A change that alters what is valid needs a new format version. From format 3.0 on, every published version stays readable.
  4. Prefer established standards (RFC 8785, RFC 8032, RFC 6962, RFC 9562) over new constructions.

This website’s format page, SDK and CLI references are generated from the package’s SPEC.md and README.md (scripts/sync_docs.py in the website’s sources); fix the source, not the generated page.
